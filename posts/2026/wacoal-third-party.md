ページスピードの改善には数多くの手法がある。しかしそれらを一通り試しても、思ったような成果が得られなかった経験を持つ人も多いはずだ。

実は重いサイトの主原因は、サードパーティタグの詰め込みにあることが多い。例をひとつ示す。

## ワコールウェブストアのページスピード

ワコールは女性用下着でおなじみのブランドで、その公式通販サイトが「ワコールウェブストア」である。このトップページを題材に、ページスピード改善をシミュレーションしてみる。

:::info このシミュレーションについて
この記事のシミュレーションは、弊社のサイトスピード改善シミュレーション技術 [PageSpeed Quest](https://github.com/ideamans/pagespeed-quest/blob/main/README.ja.md) を用いて、研究目的で自主的に行ったものです。ワコール社からの依頼によるものではありません。公開されているページを外部から計測したもので、同社の内部事情や技術的な制約は考慮していません。掲載の取り下げを希望される場合は、[お問い合わせ](https://www.ideamans.com/inquiry/)からご連絡ください。
:::

ワコールウェブストアは、主要な通販サイト281サイトの中で、Lighthouseスコアが下から5%ほどの位置にあり、低い部類に入る。

<img src="/posts/2026/wacoal-third-party/score-rank-wacoal.png" alt="主要通販サイト281サイトのLighthouseスコアをよい順に並べた棒グラフ。ワコールウェブストアは41点で、281サイト中267位の位置を赤く示している" width="1000" height="420" />

:::info このグラフについて
2026年8月に、主要な通販サイトのトップページを Lighthouse（モバイル）で計測したもの。この記事のシミュレーションとは計測の方法が違うので、スコアの値は一致しない。
:::

## オリジナルの計測結果

シミュレーションでは、ワコールウェブストアのトップページを丸ごと記録し、手元で再生しながら Lighthouse（モバイル）で3回ずつ計測した。本番のサイトには手を入れていない。

オリジナルの計測結果は以下の通りだ。

| 指標 | オリジナル |
| --- | ---: |
| Lighthouseスコア | 63 |
| FCP（最初に何かが表示されるまで） | 2.9秒 |
| LCP（メインの画像が表示されるまで） | 13.2秒 |
| Speed Index | 7.1秒 |
| TBT | 40ms |
| CLS | 0.022 |
| 通信量 | 6.7MB |

メインビジュアルが表示されるまでに13秒以上かかっている。

## 第1段階 描画を止めるファイルを整理する

まずは第一段階として、次のような改善を試してみる。

| 改善 | 内容 |
| --- | --- |
| CSSの結合 | 6つに分かれていたCSSファイルを1つにまとめる |
| JavaScriptの `defer` | 自社のメインのスクリプトに `defer` を付け、ページの解析を止めないようにする |

いずれも、ページの表示が始まるまでの時間を短くするための定番の改善である。

この結果、Lighthouseのスコアは以下のように変化した。動画もぜひ再生いただきたい。

| 指標 | オリジナル | 第1段階 |
| --- | ---: | ---: |
| Lighthouseスコア | 63 | **70** |
| FCP | 2.9秒 | **1.1秒** |
| LCP | 13.2秒 | **11.3秒** |
| Speed Index | 7.1秒 | **5.8秒** |

FCPが大きく改善し、スコアも1割ほど伸びたが、動画で見ると速くなったとは言い難い。

## 第2段階 画像とフォントを最適化する

続いて以下の改善を加える。

| 改善 | 内容 |
| --- | --- |
| LCP画像の優先読み込み | メインビジュアルの画像に `fetchpriority="high"` を付ける |
| LCP画像のWebP化 | メインビジュアルの画像をWebPに変換する |
| カルーセルの遅延読み込み | 最初は見えないスライドの画像に `loading="lazy"` を付ける |
| 残りの画像のWebP化 | ほかの画像37ファイルもWebPに変換する |
| スクリプトの移動 | `<head>` の中のスクリプトを `</body>` の直前へ移す |
| Webフォントの削除 | Google Fontsをやめ、端末のフォントを使う |
| 不要なCSSの削除 | 使っていないjQuery UIのCSSを外す |

この結果は以下の通りだ。

<img src="/posts/2026/wacoal-third-party/panel-stage2.png" alt="Lighthouseの結果パネルの比較。左の第1段階の改善後はスコア70、右の第2段階の改善後はスコア71" width="1000" height="473" />

<video src="/posts/2026/wacoal-third-party/stage2.mp4" controls muted playsinline preload="metadata" width="1024" height="784"></video>

| 指標 | 第1段階 | 第2段階 |
| --- | ---: | ---: |
| Lighthouseスコア | 70 | **71** |
| FCP | 1.1秒 | **0.8秒** |
| LCP | 11.3秒 | **9.6秒** |
| Speed Index | 5.8秒 | **5.4秒** |
| 通信量 | 6.7MB | **5.1MB** |

指標とスコアに劇的な変化はない。

ここでは画像最適化を行った。画像最適化はサイトスピード改善の本命と思われているし、実際にデータ通信量も6.7MBから5.1MBへ減った（画像だけなら2.8MBから1.2MBと半分以下）。しかしメインビジュアルの出現もワンテンポ速くなった程度で、指標とスコアはほとんど動いていない。

これはどういうことだろうか。

## サードパーティタグを外す

当然ながらワコールウェブストアでも、Google Tag Managerなどを起点に、数多くのサードパーティタグを利用している。

| 外したもの | 主な役割 |
| --- | --- |
| Google Tag Manager とその配下のタグ | アクセス解析・広告の計測など |
| Adobe Experience Platform Launch | タグの管理 |
| Yottaa | スクリプトの読み込み順の制御 |
| Brightcove | 動画の配信 |
| STAFF START | スタッフのコーディネートやレビューの表示 |
| CQuotient | レコメンド |

試しに一度これらを取り払ってみよう。すると指標と体感スピードは以下のように変化する。

<img src="/posts/2026/wacoal-third-party/panel-stage3.png" alt="Lighthouseの結果パネルの比較。左の第2段階の改善後はスコア71、右のサードパーティタグを外した後はスコア100" width="1000" height="473" />

<video src="/posts/2026/wacoal-third-party/stage3.mp4" controls muted playsinline preload="metadata" width="1024" height="784"></video>

| 指標 | 第2段階 | タグを外した後 |
| --- | ---: | ---: |
| Lighthouseスコア | 71 | **100** |
| FCP | 0.8秒 | **0.05秒** |
| LCP | 9.6秒 | **0.1秒** |
| Speed Index | 5.4秒 | **0.8秒** |
| 通信量 | 5.1MB | **1.6MB** |
| リクエスト数 | 217 | **107** |

指標やスコアもそうだが、体験スピードも比べ物にならないほど速くなった。

:::info タグを外すと機能も消える
タグを外した状態では、スタッフのコーディネート（STAFF START）の画像の枠と、動画（Brightcove）の区画が空になっている。タグを外せば速くなるのは確かだが、それは同時に、これらの機能に払っているコストでもある。
:::

### ページ自体の作りは悪くない

ちなみに、第1段階と第2段階のサイト本体の改善をせず、**オリジナルのページからサードパーティタグだけを外す**と、スコアは98になる。

ワコールウェブストアのページ自体の作りは、もともとそこまで悪くない。ページのスピードを大きく下げていたのは、サードパーティタグのほうだったことになる。

## なぜこのような現象が起こるか

サードパーティタグはサイト運営に不可欠な機能ではあるが、空気のように軽いわけではない。

ワコールウェブストアのトップページを初めて開くとき、インターネットの通信における「サイトコンテンツ自体とサードパーティ関連の通信量の割合」は以下の通りだ。

<img src="/posts/2026/wacoal-third-party/wacoal-network-share.png" alt="ワコールウェブストアのトップページの通信量の内訳。サードパーティが3.5MBで52.4%、サイト自体が3.2MBで47.6%" width="1000" height="200" />

6.7MBの通信のうち、半分以上の3.5MBがサードパーティ関連である。商品の写真やページそのものより、タグのほうが多い。

もうひとつ、Webページの表示もコンピュータープログラムによる処理なので、端末のCPUがいかに効率よく使われているかが重要だ。

今回の仮想スマートフォン端末におけるシミュレーションで、CPU消費時間は以下の割合となる。

<img src="/posts/2026/wacoal-third-party/wacoal-cpu-share.png" alt="ワコールウェブストアのトップページのCPU時間の内訳。サードパーティのスクリプトが1.62秒で65.9%、サイト自体のスクリプトが0.57秒で23.4%、描画などが0.26秒で10.7%" width="1000" height="200" />

CPU時間の3分の2を、サードパーティのスクリプトが使っている。

しかも、この数字は控えめに出ている。タグが呼び出した処理（ページの書き換えや描画など）は、サイト自体の処理として数えられることが多いからだ。オリジナルのページからタグだけを外して比べると、CPU時間は2.45秒から0.26秒へと**9割近く減る**。

<img src="/posts/2026/wacoal-third-party/wacoal-cpu-cut.png" alt="ワコールウェブストアのトップページのCPU時間の比較。オリジナルは2.45秒、サードパーティタグなしは0.26秒で、サードパーティタグ削除で89%減る" width="1000" height="300" />

ネットワーク通信、端末におけるCPU消費においても、サードパーティタグ関連の方が多くを占めている。

つまりユーザーはこのトップページを表示するとき、自分が見たいコンテンツより、目に見えない企業のための計測などに、通信と端末パワーの大部分を消費しているのだ。

サイト本体のスピード改善をいくら頑張っても成果が出ない理由はここにある。サードパーティタグの存在の方が大きく、通信や処理性能の足を引っ張っているからだ。

## 小さな改善は無意味か

今回、サードパーティタグの存在が大きく、サイト自体の改善では大きな成果が出ないと解説したが、これらの改善は無意味だろうか。

決してそのようなことはない。実はユーザーがサイトを離脱する基準は「遅い・速い」ではない。「速い・爆速」のあいだに境目がある（[「通販サイトが遅いと損失はどのくらい？」](/posts/2026/speed-opportunity-loss.html)で詳しく解説した）。

サイト自体に行った改善策は、すでに速い体験をしているユーザーを爆速にするための施策であることが多い。特にFCPの改善は重要で、CVRの改善に寄与するはずだ。

あくまでLighthouseによる計測シミュレーションでは目立った数値が出ず、説明が難しいだけで、対応することに意味はある。

## サードパーティタグなしでは運用できないのか

今回、ワコールを取り上げさせてもらったが、このようにサードパーティタグがサイト本体のためのリソースを逆転して食ってしまっているサイトは珍しくない。

これには「仕方ないだろ」という反論もあるだろう。現在のサイトを、サードパーティタグ抜きで効率よく運用できないのは常識だ。

ところが[アップルの公式サイト](https://www.apple.com/jp/)を見ると、サードパーティタグは一切利用していない。アクセス解析も含めて、読み込まれるスクリプトはすべて自社のドメインから配信されている（詳しくは[「Appleサイトはサードパーティタグを使っていない」](/posts/2024/apple-has-no-3rdparty.html)で紹介した）。

## サードパーティメタボリックに挑む

これは高速なサイト体験を増やす上で、業界全体の構造的な問題として重く考えている。

それに警鐘を鳴らすため、この記事を皮切りに、サードパーティタグが過剰に重い問題「サードパーティメタボリック」を取り扱っていきたい。
